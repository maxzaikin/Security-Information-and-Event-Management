# Методика ежедневного контроля ёмкости LogSpace

## 1. Состав

| Файл | Где работает | Назначение |
|---|---|---|
| `scripts/collect_logspace_metrics.sh` | MP SIEM Events Storage | Каждый запуск пишет новый файл `logspace_metrics_<дата запуска>.csv` |
| `logspace_metrics_<ГГГГ-ММ-ДД>.csv` | MP SIEM Events Storage | Результат запуска за одну дату; файлы прошлых дней сохраняются |
| Excel-файл (например `I:\SHARE\AN\metrics.xlsx`) | рабочая станция | Накопительный файл; единственный источник данных для ноутбука |
| `notebooks/logspace_capacity.ipynb` | Jupyter | Анализ, прогнозы, ежедневная сводка |

Что собирает скрипт за один запуск:

- **events** — количество событий по `event_src_category` за сутки. Агрегация (GROUP BY) выполняется в LogSpace, сырые события не выгружаются. Пустая категория записывается как `Not_Normalized`.
- **partition** — размеры разделов из `backup_tool --cmd listpart`.
- **disk** — `df` для каталога данных LogSpace: total, used, avail. Для гибридного режима дополнительно `cold_*` (переменная `COLD_PATH`).
- **health** — есть ли tailcutter в cron и сколько минут назад обновлялся его журнал.

Формат файла: `collected_at;metric_date;record_type;key;value`, даты в `ДД.ММ.ГГГГ`. Каждый запуск создаёт **отдельный файл** с датой запуска в имени, файлы прошлых дней не трогаются. Поэтому после выходных или отпуска на сервере лежат файлы за все пропущенные дни, и динамика не теряется. Ручные запуски получают суффикс и не затирают ежедневный файл:

| Запуск | Имя файла |
|---|---|
| ежедневный (cron) | `logspace_metrics_2026-10-13.csv` |
| `-d 2026-10-10` | `logspace_metrics_2026-10-13_day_2026-10-10.csv` |
| `-f 2026-01-01 -t 2026-10-12` | `logspace_metrics_2026-10-13_backfill_2026-01-01_2026-10-12.csv` |
| `-S` | `logspace_metrics_2026-10-13_snapshot.csv` |

Повторный запуск того же вида в ту же дату перезаписывает свой файл. Старые файлы скрипт не удаляет. История для ноутбука хранится в Excel-файле на рабочей станции. Повторное добавление одних и тех же строк безопасно: ноутбук берёт строку с самым поздним `collected_at`.

## 2. Первичная настройка

1. Скопируйте скрипт на Events Storage, например в `/opt/siem-metrics/`, и выполните `chmod +x`.
2. Проверьте путь к данным. В `config.xml` LogSpace это параметр `path` (по умолчанию `/opt/logspaced`). Если путь другой, задайте `DATA_PATH=...`.
3. Заполните историю один раз, в нерабочее время:
   ```
   ./collect_logspace_metrics.sh -f 2026-01-01 -t <вчера>
   ```
   Скрипт выполняет один агрегирующий запрос на каждый день, прогресс виден в `logspace_metrics.log`. Начальную дату берите по самому старому разделу из `listpart`.
   Получившийся CSV перенесите в Excel-файл целиком, вместе с заголовком: это начало накопительного файла.
4. Добавьте ежедневный запуск в cron:
   ```
   30 12 * * * cd /opt/siem-metrics && ./collect_logspace_metrics.sh >> cron.out 2>&1
   ```
  
5. На рабочей станции: `pip install -r requirements.txt` (pandas, numpy, scipy, plotly, tqdm, openpyxl, statsmodels). Без `statsmodels` ноутбук работает, но пропускает модель SARIMAX.
6. Старую историю из Excel можно подключить: в ноутбуке задайте `LEGACY_XLSX = Path("eps.xlsx")`. Данные скрипта имеют приоритет над ней.

## 3. Ежедневный регламент (5–10 минут)

1. Скопируйте с сервера все файлы `logspace_metrics_*.csv`, появившиеся с прошлого переноса (после выходных их несколько).
2. По очереди, от старой даты к новой, откройте каждый в Excel, выделите все строки **кроме заголовка** и вставьте их в накопительный Excel-файл сразу под последней заполненной строкой. Сохраните как `.xlsx`.
3. `Kernel → Restart & Run All`.
4. Откройте **раздел 10 (Daily summary)** и разберите каждую строку не в статусе OK, по столбцу `see`.
5. Если всё в OK, достаточно взглянуть на графики разделов 7 и 8: не сдвинулась ли дата начала ротации и глубина хранения по сравнению со вчерашним днём.

## 4. Что означает каждая проверка и что делать

| Проверка | WARN / CRIT означает | Действие |
|---|---|---|
| latest snapshot age | Скрипт не запускался больше суток | Проверьте cron и `logspace_metrics.log` на сервере |
| events collected up to | Нет событий за вчера | Ошибка запроса в журнале скрипта; дозапустите `-d <дата>` |
| volume vs same weekday | Суточный объём отличается от того же дня недели больше чем на 30% | Рост — шум, новый источник или атака; падение — потеря источников. Смотрите раздел 4 и проверяйте сбор |
| categories off baseline | Конкретные категории ушли больше чем на 50% | Источник перестал присылать события (−) или начал заливать (+). Это самый ранний сигнал проблем со сбором |
| D drift | Стоимость события изменилась больше чем на 10% | Сменился состав событий: пошли «тяжёлые» категории или длинные сообщения. Пересчитайте прогноз через 1–2 недели |
| partitions / limit | **WARN > 95%, CRIT > 102%** | CRIT означает, что разделы превысили лимит и tailcutter их не удаляет. Ротация не работает, см. раздел 6 |
| size rotation starts in | Ротация по объёму начнётся меньше чем через 30 дней | Решение: принять сокращение глубины хранения, расширить диск или отфильтровать источники (раздел 9) |
| physical free space | Свободного места меньше, чем `1 − DBSPACE` (WARN) или меньше 5% (CRIT) | Если разделы в пределах лимита, место занимает что-то кроме них (раздел 3) |
| tailcutter in cron | **CRIT**: задачи нет | Восстановите задачу (раздел 6) |
| tailcutter log age | Журнал не обновлялся больше 90 минут | tailcutter не запускается или падает: смотрите журнал |

## 5. Как читать графики

**Раздел 2 — bytes vs events, D over time.**
Норма: точки вытянуты вдоль красной линии, R² близок к 1. Тогда расход диска определяется числом событий, и прогноз через EPS надёжен. Разница между красной и чёрной пунктирной линией показывает, насколько формула вендора (200 байт на событие) расходится с вашей реальностью. Ступенька на графике D при ровном EPS означает, что изменился состав событий, а не поток.

**Раздел 3 — df used / partitions.**
Норма: отношение стабильно и близко к 1,0–1,05. Это доказывает, что `bytes` из `listpart` соответствует реальному месту на диске. Если отношение растёт, диск занимает что-то помимо разделов (staging, metadata, сторонние файлы), и tailcutter с этим не справится.

**Раздел 4 — category share и тренды.**
Площадной график показывает, из чего состоит поток. Столбики — рост категорий в % за месяц. Нужно смотреть на две вещи: какие категории растут быстрее всех (они определяют будущий расход) и резкие изменения доли (подключили или потеряли источник).

**Раздел 5 — стоимость категорий.**
Это ГиБ в сутки, которые занимает каждая категория. Усы — интервал p5…p95. Если ус короткий, оценке можно доверять, и её можно использовать для решения «что фильтровать». Если длинный, данных пока мало: модель надёжна после 3 и более месяцев истории событий. Группа `other <1%` объединяет мелкие категории, её коэффициент обычно неустойчив.

**Раздел 6 — бэктест.**
Каждая модель обучается без последних 28 дней и проверяется на них. Чем меньше MAPE, тем лучше модель; лучшая используется дальше автоматически. `bias` — систематическая ошибка: минус означает, что модель занижает. Если MAPE лучшей модели выше 15%, в последних неделях был резкий сдвиг режима, и долгосрочному прогнозу доверять нельзя.

- **Linear** — продолжает средний темп роста за `TREND_WINDOW` дней. Хорош при ровном росте, но «запоминает» прошлые скачки.
- **Holt-Winters** — быстро подстраивается под новый уровень, рост затухает (damped trend). Склонен к консервативному прогнозу.
- **SARIMAX** — сезонная ARIMA с недельным циклом и дрейфом, обучается на последних `SARIMAX_WINDOW` днях (по умолчанию 180). Учитывает, как отклонение одного дня переходит на следующие, и продолжает средний рост окна. Порядок модели задаётся в настройках (`SARIMAX_ORDER`, `SARIMAX_SEASONAL_ORDER`); если бэктест стабильно хуже других моделей, его можно подобрать.

**Раздел 7 — прогноз суточного объёма и EPS.**
Слева от пунктирной вертикали — история, справа — прогноз (7-дневные средние). Толстая линия — лучшая модель, пунктир — остальные. Затенённая полоса — разброс между моделями плюс типичная ошибка. Широкая полоса означает, что модели расходятся во мнениях о будущем, то есть в истории недавно был сдвиг. В таком случае ориентируйтесь на ближайшие 2–4 недели и смотрите, к какой линии приближается факт.

**Раздел 8 — ёмкость.** Это главные графики раздела.
- *Occupied by partitions.* Серый пунктир — сколько занимали бы разделы без ротации по объёму. Синяя линия — ожидаемое заполнение с ротацией. Красная — лимит `DBSPACE`. Точка пересечения серого с красным — дата, когда tailcutter начнёт удалять старые дни.
- *Retention depth.* Сколько дней событий будет храниться на каждую будущую дату. Это бизнес-метрика: требования к глубине хранения (регуляторные, внутренние) сравнивайте именно с ней. При росте потока она падает.
- *Physical free space.* Синяя линия — прогноз `df avail` с учётом ротации. Оранжевая — простое продолжение текущего тренда `df`, то есть сценарий «ротация не работает». Её пересечение с нулём — дата переполнения диска, если ничего не делать.

**Раздел 9 — «что если».**
Таблица показывает, как изменится суточный объём и глубина хранения при изменении всего потока на ±X%. Функция `what_if_category("Firewall", -30)` считает то же для одной категории, а интервал берёт из раздела 5. Используйте её для обоснования фильтрации источников или расширения диска.

## 6. Если ротация не работает

1. Есть ли задача: `grep -r tailcutter /etc/cron* /var/spool/cron`.
2. Журнал: `tail -n 100 /opt/dbtools/log/tailcutter.log`.
3. Ручной запуск с подробным журналом:
   `/opt/dbtools/bin/tailcutter --dbspace 85% --ttl 365 --loglevel DEBUG`
4. Постоянные параметры задаются в конфигурации роли Event Storage (`TailcutterDbspace`, `TailcutterTtl`, `TailcutterTtlc`) через Deployer.
5. Удалять день вручную можно только штатно: `backup_tool --cmd deletepart --part <раздел>`. Никогда не через `rm` в каталоге данных. Перед удалением можно заархивировать: `backup --from ... --to ... --delete-part true` от пользователя `logspace`.

## 7. Еженедельно и ежемесячно

- **Раз в неделю:** сравните дату начала ротации и глубину хранения с прошлой неделей. Сдвиг больше чем на неделю — повод разобраться, какая категория его вызвала (разделы 4 и 5).
- **Раз в месяц:** проверьте, какая модель лучшая и не изменилась ли она; подберите `TREND_WINDOW` (30 / 90 / 180) по бэктесту; зафиксируйте прогноз глубины хранения для планирования закупки дисков.

## 8. Ограничения

- Ни один прогноз не предскажет подключение новых источников или их отключение. После таких событий модели нужно 2–3 недели, чтобы адаптироваться.
- Часовой пояс `_eventDate` и разделов `listpart` не проверен (раздел 2, п. 4).
- Лимит в ноутбуке считается как `DBSPACE × df total`, по описанию tailcutter в документации («92% от общего объёма дискового пространства»). Если в вашей версии tailcutter считает иначе, даты начала ротации будут смещены. Проверить можно по журналу tailcutter в момент первого удаления.
- В режиме гибридного хранилища скрипт собирает `cold_*`, но ноутбук прогнозирует только основной путь. Как tailcutter учитывает холодное хранилище, я не знаю.
