# Методика ежедневного контроля ёмкости LogSpace

## 1. Состав

| Файл | Где работает | Назначение |
|---|---|---|
| `scripts/collect_logspace_metrics.sh` | MP SIEM Events Storage | Каждый запуск пишет новый файл `logspace_metrics_<дата запуска>.csv` |
| `logspace_metrics_<ГГГГ-ММ-ДД>.csv` | MP SIEM Events Storage | Результат запуска за одну дату; файлы прошлых дней сохраняются |
| Excel-файл (например `I:\SHARE\AN\metrics.xlsx`) | рабочая станция | Накопительный файл; единственный источник данных для ноутбука |
| `notebooks/logspace_capacity.ipynb` | Jupyter | Анализ, прогнозы, ежедневная сводка |

Что собирает скрипт за один запуск:

- **events** — количество событий по `event_src_category` за сутки. Агрегация (GROUP BY) выполняется в LogSpace, сырые события не выгружаются. Пустая категория записывается как `Not_Normalized`.
- **partition** — размеры разделов из `backup_tool --cmd listpart`.
- **disk** — `df` для каталога данных LogSpace: total, used, avail. Для гибридного режима дополнительно `cold_*` (переменная `COLD_PATH`).
- **health** — есть ли tailcutter в cron и сколько минут назад обновлялся его журнал.

Формат файла: `collected_at;metric_date;record_type;key;value`, даты в `ДД.ММ.ГГГГ`. Каждый запуск создаёт **отдельный файл** с датой запуска в имени, файлы прошлых дней не трогаются. Поэтому после выходных или отпуска на сервере лежат файлы за все пропущенные дни, и динамика не теряется. Ручные запуски получают суффикс и не затирают ежедневный файл:

| Запуск | Имя файла |
|---|---|
| ежедневный (cron) | `logspace_metrics_2026-10-13.csv` |
| `-d 2026-10-10` | `logspace_metrics_2026-10-13_day_2026-10-10.csv` |
| `-f 2026-01-01 -t 2026-10-12` | `logspace_metrics_2026-10-13_backfill_2026-01-01_2026-10-12.csv` |
| `-S` | `logspace_metrics_2026-10-13_snapshot.csv` |

Повторный запуск того же вида в ту же дату перезаписывает свой файл. Старые файлы скрипт не удаляет. История для ноутбука хранится в Excel-файле на рабочей станции. Повторное добавление одних и тех же строк безопасно: ноутбук берёт строку с самым поздним `collected_at`.

## 2. Первичная настройка

1. Скопируйте скрипт на Events Storage, например в `/opt/siem-metrics/`, и выполните `chmod +x`.
2. Проверьте путь к данным. В `config.xml` LogSpace это параметр `path` (по умолчанию `/opt/logspaced`). Если путь другой, задайте `DATA_PATH=...`.
3. Заполните историю один раз, в нерабочее время:
   ```
   ./collect_logspace_metrics.sh -f 2026-01-01 -t <вчера>
   ```
   Скрипт выполняет один агрегирующий запрос на каждый день, прогресс виден в `logspace_metrics.log`. Начальную дату берите по самому старому разделу из `listpart`.
   Получившийся CSV перенесите в Excel-файл целиком, вместе с заголовком: это начало накопительного файла.
4. Добавьте ежедневный запуск в cron:
   ```
   30 12 * * * cd /opt/siem-metrics && ./collect_logspace_metrics.sh >> cron.out 2>&1
   ```
  
5. На рабочей станции: `pip install -r requirements.txt` (pandas, numpy, scipy, plotly, tqdm, openpyxl, statsmodels). Без `statsmodels` ноутбук работает, но пропускает модель SARIMAX.
6. Сутки в LogSpace — по UTC (`_eventDate` и разделы), а время в CSV — местное время сервера. Задайте в разделе 0 ноутбука `SERVER_UTC_OFFSET_H` — разницу «местное − UTC» по выводу `date; date -u` на сервере (например, для UTC+11 → 11). Скрипт по умолчанию берёт «вчера» по UTC, поэтому время запуска cron может быть любым. Даты в `-d` и `-f … -t …` — тоже сутки UTC. Подсчёты событий, снятые до окончания суток UTC (старая версия скрипта при ночном запуске), ноутбук не использует и печатает команду для их перевыгрузки.
   Перенесите в раздел 0 ноутбука параметры tailcutter из `/opt/dbtools/etc/tailcutter.yml`: `dbspace` → `DBSPACE` (97% → `0.97`), `ttl` → `TTL_DAYS`. Не подбирайте `DBSPACE` по графикам: это настройка сервера (раздел 6).
7. Задайте лимит лицензии MaxPatrol 10: `EPS_LICENSE = <лимит EPS>` в разделе 0 ноутбука. Правила проверки (допуск +30% для среднего за сутки, 20 дней из 90, уведомления по неделе +20% и месяцу +10%) взяты из статьи PT «Лимит EPS: условия и ограничения лицензионного контроля» (справка MaxPatrol 10, 27.2) и вынесены в параметры `EPS_*`. EPS в ноутбуке — это события, сохранённые в LogSpace за сутки, делённые на 86 400. Сверьте его один раз с виджетом PT MC «Средний поток событий» за те же дни: какие события считает лицензия, в статье не указано.
8. Старую историю из Excel можно подключить: в ноутбуке задайте `LEGACY_XLSX = Path("eps.xlsx")`. Данные скрипта имеют приоритет над ней.

## 3. Ежедневный регламент (5–10 минут)

1. Скопируйте с сервера все файлы `logspace_metrics_*.csv`, появившиеся с прошлого переноса (после выходных их несколько).
2. По очереди, от старой даты к новой, откройте каждый в Excel, выделите все строки **кроме заголовка** и вставьте их в накопительный Excel-файл сразу под последней заполненной строкой. Сохраните как `.xlsx`.
3. `Kernel → Restart & Run All`.
4. Откройте **раздел 10 (Daily summary)** и разберите каждую строку не в статусе OK, по столбцу `see`.
   Затем **раздел 11 (сравнение с прошлыми днями)**: что стало лучше или хуже по сравнению с тем же днём прошлой недели и как сдвинулся прогноз. Для сравнения нужны данные за каждый день и папка `export/` с выгрузками прошлых запусков — не очищайте её.
5. Если всё в OK, достаточно взглянуть на графики разделов 7 и 8: не сдвинулась ли дата начала ротации и глубина хранения по сравнению со вчерашним днём.

## 4. Что означает каждая проверка и что делать

| Проверка | WARN / CRIT означает | Действие |
|---|---|---|
| latest snapshot age | Скрипт не запускался больше суток | Проверьте cron и `logspace_metrics.log` на сервере |
| events collected up to | Нет событий за вчера | Ошибка запроса в журнале скрипта; дозапустите `-d <дата>` |
| volume vs same weekday | Суточный объём отличается от того же дня недели больше чем на 30% | Рост — шум, новый источник или атака; падение — потеря источников. Смотрите раздел 4 и проверяйте сбор |
| categories off baseline | Конкретные категории ушли больше чем на 50% | Источник перестал присылать события (−) или начал заливать (+). Это самый ранний сигнал проблем со сбором |
| events without a category | Доля событий без категории за 28 дней выше `WARN_NOT_NORMALIZED` (10%) | Эти события занимают диск, но почти не работают на корреляцию. По разделу 4.3 найдите день роста доли и источник; исправьте нормализацию |
| largest level change in events | Информационная строка: дата и размер самого заметного изменения потока | Какие категории его дали — раздел 4.5 |
| deleted since the previous snapshot | **WARN**, если удалён день не с краю (не самый старый) | tailcutter удаляет только самые старые дни: это ручной `deletepart` или сбой. Выясните, кто и зачем (раздел 3b) |
| deletions vs DBSPACE | **WARN**: дни удаляются, когда диск заполнен меньше порога `DBSPACE` (заполнение до удаления оценивается как «занято после + удалено») | tailcutter по объёму ниже своего порога не удаляет, значит это ручной `deletepart` — или tailcutter считает заполнение от другой базы, чем `df` (вопрос к PT). `DBSPACE` не подгоняйте под это значение: он должен совпадать с `dbspace` в `tailcutter.yml` |
| D drift | Стоимость события изменилась больше чем на 10% | Сменился состав событий: пошли «тяжёлые» категории или длинные сообщения. Пересчитайте прогноз через 1–2 недели |
| partitions / limit | **WARN > 95%, CRIT > 102%** | CRIT означает, что разделы превысили лимит и tailcutter их не удаляет. Ротация не работает, см. раздел 6 |
| size rotation starts in | Ротация по объёму начнётся меньше чем через 30 дней | Решение: принять сокращение глубины хранения, расширить диск или отфильтровать источники (раздел 9) |
| days that fit at today's flow vs required | **CRIT**: при сегодняшнем потоке (среднее за 7 дней) в лимит помещается меньше дней, чем `RETENTION_REQUIRED` (требование закона, по умолчанию 365) | Диск не обеспечивает обязательную глубину хранения. Сколько не хватает в ТиБ, показывает раздел 8 (оранжевая линия); варианты — расширение диска или фильтрация (раздел 9) |
| retention at the horizon vs required | **WARN**: к концу горизонта прогноза глубина хранения опустится ниже `RETENTION_REQUIRED` | Решение нужно принять до того, как нижняя граница полосы на графике глубины хранения пересечёт красную линию |
| physical free space | Свободного места меньше, чем `1 − DBSPACE` (WARN) или меньше 5% (CRIT) | Если разделы в пределах лимита, место занимает что-то кроме них (раздел 3) |
| EPS vs licence | Средний EPS последнего дня выше лицензии (**WARN**) или выше лицензии +30% (**CRIT**: день засчитывается в лицензионную проверку). Строки есть, только если задан `EPS_LICENSE` | Найдите источник роста (разделы 4.6, 11b). Каждый засчитанный день приближает ограничения |
| days above licence +30% in the last 90 | **WARN**: есть засчитанные дни, идёт льготный период; **CRIT**: их 20 и больше — по правилу вендора функции ограничены (поиск 7 дней, без задач сбора, без корреляции) | Сократите поток ниже лимита; выход из льготного периода — 90 дней подряд без превышений |
| weekly / monthly average vs licence | Среднее за неделю выше +20% или за месяц выше +10%: PT MC присылает уведомления, ограничений нет | Ранний сигнал: поток устойчиво выше лицензии |
| licence in the forecast | По суточному прогнозу лучшей модели будет первый засчитанный день и дата, когда их станет 20 за 90 дней | Решение до этой даты: расширение лицензии или фильтрация (раздел 9, столбец `licence`) |
| tailcutter in cron | **CRIT**: задачи нет | Восстановите задачу (раздел 6) |
| tailcutter log age | Журнал не обновлялся больше 90 минут | tailcutter не запускается или падает: смотрите журнал |

## 5. Как читать графики

**Раздел 1 — daily volume и daily events.**
Два графика за весь период: размер раздела каждого дня (ГиБ) и число событий каждого дня (млн). Если оба двигаются вместе, изменился поток. Если объём изменился, а число событий нет, изменился вес события (см. D в разделе 2). День без столбца на графике событий означает, что события за него не собраны, нужен дособор `-f … -t …`.

**Раздел 1c — средний EPS за сутки против лицензии.** Столбцы — средний поток за сутки (события дня / 86 400) по трём показателям вендора. Синие столбцы — в пределах лицензии. Оранжевые — выше лицензии, но в допуске +30%, последствий нет. Красные — выше +30%: такой день засчитывается, 20 таких дней за 90 вводят ограничения. Чёрная линия — среднее за неделю, уведомление выше +20%. Серая пунктирная — среднее за месяц, уведомление выше +10%. В заголовке — число засчитанных дней за 90. Лимит задаётся в `EPS_LICENSE` в рабочей копии ноутбука; в репозиторий его не коммитим.

**Раздел 2 — bytes vs events, D over time.**
Норма: точки вытянуты вдоль красной линии, R² близок к 1. Тогда расход диска определяется числом событий, и прогноз через EPS надёжен. Разница между красной и чёрной пунктирной линией показывает, насколько формула вендора (200 байт на событие) расходится с вашей реальностью. Ступенька на графике D при ровном EPS означает, что изменился состав событий, а не поток.

**Раздел 2 — D check.** По каждому дню два столбца: фактический размер дня и «события дня × `D_FACT`». Чёрная линия показывает ошибку такой оценки в %. Норма: столбцы одной высоты, линия около 0 в последние недели. В печати под графиком приводятся медиана ошибки и доля дней в пределах ±10% за 28 дней. Если линия стабильно выше или ниже 0, коэффициент D смещён, и пересчёт между EPS и байтами в разделах 7–9 ошибается на эту величину.

**Раздел 3 — df used / partitions.**
Норма: отношение стабильно и близко к 1,0–1,05. Это доказывает, что `bytes` из `listpart` соответствует реальному месту на диске. Если отношение растёт, диск занимает что-то помимо разделов (staging, metadata, сторонние файлы), и tailcutter с этим не справится.

**Раздел 4 — category share и тренды.**
Площадной график показывает, из чего состоит поток. Столбики — рост категорий в % за месяц. Нужно смотреть на две вещи: какие категории растут быстрее всех (они определяют будущий расход) и резкие изменения доли (подключили или потеряли источник).

**Разделы 4.3–4.8 — анализ событий.** Строятся по событиям по категориям, нужно от 2 до 8 недель истории (дособор `-f … -t …`).
- **4.3** — доля событий без категории по дням: показатель качества нормализации.
- **4.4** — сколько категорий дают 80% событий: только о них имеет смысл говорить при оптимизации.
- **4.5** — самое заметное изменение уровня потока и вклад каждой категории в него: новый источник это или общий рост.
- **4.6** — дни-всплески относительно того же дня недели и категории, которые их дали.
- **4.7** — недельный профиль: поток «машин» (почти не меняется в выходные) и поток «людей» (рабочие часы). Фоновый машинный поток — первое место для поиска шума.
- **4.8** — карта сбора: каждая категория каждый день относительно своего обычного уровня. Красное — источник замолчал; таблица со стабильностью и «тихими» днями.

**Раздел 7 — прогноз событий по категориям.** Для каждой основной категории своя модель (по её собственному бэктесту), прогноз на горизонт и таблица «сейчас / через 30 / 90 / 180 дней». Показывает, какие категории сформируют будущий поток.

**Раздел 11b — прошедший день по категориям.** Последний полный день с событиями сравнивается по каждой категории с предыдущим днём и с тем же днём недели неделю назад. Работает с первых дней сбора, до того как разделам 4.x хватит истории. Категория, упавшая почти до нуля, означает, что источник замолчал. Кратный рост против обоих дней означает флуд или новый источник. Честное сравнение — с тем же днём недели; сравнение с предыдущим днём включает недельный ритм. Кнопка *log* показывает мелкие категории.

Подробные пояснения к каждому графику и таблице — в ячейках *How to read* книги.

**Раздел 5 — стоимость категорий.**
Это ГиБ в сутки, которые занимает каждая категория. Усы — интервал p5…p95. Если ус короткий, оценке можно доверять, и её можно использовать для решения «что фильтровать». Если длинный, данных пока мало: модель надёжна после 3 и более месяцев истории событий. Группа `other <1%` объединяет мелкие категории, её коэффициент обычно неустойчив.

**Подсказки.** При наведении на день подсказка показывает не только значение линии, но и связанные величины: события в млн, D, EPS, сколько дней такого потока помещается в лимит, отклонение от обычного уровня, вклад категорий.

**Раздел 6 — бэктест.**
Справа от линии *last complete day* — прогноз лучшей модели на ближайшие `NEAR_HORIZON` дней (по умолчанию 30) с полосой ± её MAPE. Он продолжает ту же динамику, которую бэктест только что проверил; таблица `near_forecast` содержит прогноз по дням и сумму за период.
Каждая модель обучается без последних 28 дней и проверяется на них. Чем меньше MAPE, тем лучше модель; лучшая используется дальше автоматически. `bias` — систематическая ошибка: минус означает, что модель занижает. Если MAPE лучшей модели выше 15%, в последних неделях был резкий сдвиг режима, и долгосрочному прогнозу доверять нельзя.

- **Linear** — продолжает средний темп роста за `TREND_WINDOW` дней. Хорош при ровном росте, но «запоминает» прошлые скачки.
- **Holt-Winters** — быстро подстраивается под новый уровень, рост затухает (damped trend). Склонен к консервативному прогнозу.
- **SARIMAX** — сезонная ARIMA с недельным циклом и дрейфом, обучается на последних `SARIMAX_WINDOW` днях (по умолчанию 180). Учитывает, как отклонение одного дня переходит на следующие, и продолжает средний рост окна. Порядок модели задаётся в настройках (`SARIMAX_ORDER`, `SARIMAX_SEASONAL_ORDER`); если бэктест стабильно хуже других моделей, его можно подобрать.

**Раздел 7 — прогноз суточного объёма и EPS.**
Слева от пунктирной вертикали — история, справа — прогноз (7-дневные средние). Толстая линия — лучшая модель, пунктир — остальные. Затенённая полоса — разброс между моделями плюс типичная ошибка. Широкая полоса означает, что модели расходятся во мнениях о будущем, то есть в истории недавно был сдвиг. В таком случае ориентируйтесь на ближайшие 2–4 недели и смотрите, к какой линии приближается факт.
На графике EPS при заданном `EPS_LICENSE`: оранжевая пунктирная линия — лицензия, красная — лицензия +30%. Оранжевые точки — фактические дни выше лицензии, но в допуске; красные крестики — дни выше +30%, они засчитываются. Серая точечная линия — суточный прогноз лучшей модели, полые крестики — прогнозные засчитанные дни. Лицензия считает дни, поэтому рабочие дни пересекают линию раньше, чем среднее за 7 дней. Красные вертикали — первый прогнозный засчитанный день и дата, когда засчитанных дней станет 20 за 90.
Красная пунктирная линия на графике объёма — максимальный суточный объём, при котором диск ещё держит `RETENTION_REQUIRED` дней: (лимит − прочие разделы) / требуемые дни. Это оценка для установившегося режима. Прогноз выше линии означает, что требуемая глубина хранения не обеспечивается; под графиком печатается, когда прогноз её пересечёт.

**Раздел 8 — ёмкость.** Это главные графики раздела.
- *Occupied by partitions.* Серый пунктир — сколько занимали бы разделы без ротации по объёму. Синяя линия — ожидаемое заполнение с ротацией. Красная — лимит `DBSPACE`. Точка пересечения серого с красным — дата, когда tailcutter начнёт удалять старые дни.
- *Occupied by partitions*, оранжевая линия — сколько диска нужно, чтобы хранить `RETENTION_REQUIRED` дней: сумма последних требуемых дней истории и прогноза. Если она выше красной, диска не хватает до требования; подсказка показывает дефицит в ТиБ относительно лимита и всего диска.
- *Retention depth.* Сколько дней событий будет храниться на каждую будущую дату. Это бизнес-метрика: красная пунктирная линия — требуемая глубина `RETENTION_REQUIRED`, подсказка показывает, сколько дней не хватает. При росте потока она падает.
- *Physical free space.* Синяя линия — прогноз `df avail` с учётом ротации. Оранжевая — простое продолжение текущего тренда `df`, то есть сценарий «ротация не работает». Её пересечение с нулём — дата переполнения диска, если ничего не делать.

**Раздел 8b — объём диска под требования хранения.** Простой расчёт «события дня × D дня × требуемые дни» для двух требований: хранение событий `RETENTION_REQUIRED` дней (1 год) и архив `ARCHIVE_DAYS` дней (3 года). Тёмные столбцы — последний полный день, светлые — предыдущий. В подсказке видно, как получено число, изменение к предыдущему дню (отдельно за счёт числа событий и за счёт D) и дефицит или запас относительно текущего диска. Рядом с первой парой столбцов отмечены текущий диск и лимит ротации.
- Сравнение с предыдущим днём включает недельный ритм: понедельник против воскресенья даёт скачок в десятки процентов.
- Один день не учитывает рост. Для планирования используйте оранжевую линию раздела 8, где суммируются реальные дни и прогноз.
- Архив по умолчанию считается с тем же D, что LogSpace (`ARCHIVE_D_FACTOR = 1`). Это не проверено: когда станет известно реальное соотношение размера архива дня к его разделу в LogSpace, задайте его в разделе 0.
- Не учтены прочие разделы (counters и т. п.) и накладные расходы файловой системы (раздел 3).

**Раздел 8c — что означает `dbspace`.** Для реального диска и сегодняшнего потока: при каком объёме начинаются удаления, сколько дней хранится и какой остаётся запас при разных значениях `dbspace` (80–97% и текущем). Синие столбцы — дни хранения, красная линия — требование; оранжевые — запас в днях потока. Как работает параметр — раздел 6 методики.

**Раздел 9 — «что если».**
Над таблицей печатается базовая линия: чему равен сценарий «0 %» (сегодняшний поток за 7 дней в ГиБ/день, EPS и млн событий в сутки), из чего получено место под события (`DBSPACE` × диск − прочие разделы) и почему на диске сейчас лежит больше дней, чем поместится при сегодняшнем потоке (старые дни легче, поток вырос). Если разделы уже превышают лимит ноутбука, выводится предупреждение: проверьте, что `DBSPACE` совпадает с `dbspace` в `tailcutter.yml`; если совпадает, tailcutter считает заполнение от другой базы, чем ноутбук.
В строках — абсолютные значения сценария: EPS, события, ГиБ/день, сколько дней такого потока помещается, выполнено ли требование `RETENTION_REQUIRED` («✓ запас N дней» или «✗ не хватает N дней»), сколько ТиБ нужно на год и сколько диска надо добавить (недостающее место / `DBSPACE`).
Таблица показывает, как изменится суточный объём и глубина хранения при изменении всего потока на ±X%. Функция `what_if_category("Firewall", -30)` считает то же для одной категории, а интервал берёт из раздела 5. Используйте её для обоснования фильтрации источников или расширения диска.

## 6. Ротация: как работает tailcutter и что делать, если она не работает

### Где настраивается

tailcutter запускается из cron, например:

```
/etc/cron.d/tailcutter_logspace:
*/30 * * * * root /opt/dbtools/bin/tailcutter /opt/dbtools/etc/tailcutter.yml
```

Параметры лежат в `/opt/dbtools/etc/tailcutter.yml`:

| Параметр | Что значит |
|---|---|
| `dbspace` | Порог заполнения диска (подробно ниже). В ноутбуке — `DBSPACE` |
| `ttl` | Дни событий старше этого числа удаляются при любом заполнении. В ноутбуке — `TTL_DAYS` |
| `ttlc` | То же для разделов `counters` (счётчики), обычно несколько дней |
| `log`, `loglevel` | Журнал (`/opt/dbtools/log/tailcutter.log`) и подробность: `INFO`, `DEBUG` |
| `dry-run` | `true` — только показать, что было бы удалено, ничего не удаляя |

В документации PT эти же параметры описаны как параметры роли Event Storage (`TailcutterDbspace`, `TailcutterTtl`, `TailcutterTtlc`), задаваемые через Deployer. Перезапишет ли Deployer ручную правку `tailcutter.yml` при следующем развёртывании, я не знаю: перед правкой файла уточните у PT.

### Как работает `dbspace`

`dbspace` — это **порог, а не доля удаления**. При диске 15 ТБ и `dbspace: 85%` лимит для данных событий — 12,75 ТБ.

1. При каждом запуске tailcutter сравнивает занятое данными место с `dbspace × диск`.
2. Пока занято меньше — по объёму ничего не удаляется. В журнале: `No partitions to delete by dbspace`.
3. Когда занято больше — удаляются **самые старые дни целиком**, пока данные снова не поместятся под порог. Когда диск уже заполнен, это примерно один старый день на каждый новый день, а не 15% и не 25% данных.
4. Независимо от этого дни старше `ttl` удаляются всегда. В журнале: `Next partitions has been deleted by ttl: [...]`.

Выбор `dbspace` — компромисс между глубиной хранения и запасом свободного места. Запас — это время, за которое диск заполнится, если tailcutter остановится или поток резко вырастет. Пример для диска 15 ТБ и потока 75 ГБ в сутки (условные цифры):

| `dbspace` | Удаление начинается выше | Хранится дней | Свободный запас | Запас в днях потока |
|---|---|---|---|---|
| 85% | 12,75 ТБ | ~174 | 2,25 ТБ | ~31 |
| 90% | 13,50 ТБ | ~184 | 1,50 ТБ | ~20 |
| 95% | 14,25 ТБ | ~195 | 0,75 ТБ | ~10 |
| 97% | 14,55 ТБ | ~199 | 0,45 ТБ | ~6 |

Переход с 85% на 97% даёт около 25 дней истории, но остановившийся tailcutter заполнит диск не за месяц, а за 6 дней. Та же таблица на реальном диске и сегодняшнем потоке — раздел 8c ноутбука.

Не подтверждено вендором: что именно tailcutter сравнивает с `dbspace` — сумму разделов (так считает ноутбук), `df used` каталога данных или весь диск — и удаляет ли он ровно до порога.

### Если ротация не работает

1. Есть ли задача и принимает ли её cron: `sudo cat /etc/cron.d/tailcutter_logspace`, `ls -l /etc/cron.d/tailcutter_logspace` (владелец root, права 644), `sudo grep -i tailcutter /var/log/syslog`.
2. Журнал: `sudo tail -n 100 /opt/dbtools/log/tailcutter.log`. Запуски каждые 30 минут и `No partitions to delete by dbspace` означают, что tailcutter работает, но по его подсчёту порог не достигнут.
3. Сравните `df` каталога данных в момент ручного удаления с `dbspace`. Если вы удаляете дни раньше порога, tailcutter до них просто не доходит (раздел 3b ноутбука помечает такие удаления `below DBSPACE — manual delete?`). Если `df` выше порога, а tailcutter пишет, что удалять нечего, он считает заполнение от другой базы — это вопрос к PT.
4. Удалять день вручную можно только штатно: `backup_tool --cmd deletepart --part <раздел>`. Никогда не через `rm` в каталоге данных. Перед удалением можно заархивировать: `backup --from ... --to ... --delete-part true` от пользователя `logspace`.

## 7. Еженедельно и ежемесячно

- **Раз в неделю:** сравните дату начала ротации и глубину хранения с прошлой неделей. Сдвиг больше чем на неделю — повод разобраться, какая категория его вызвала (разделы 4 и 5).
- **Раз в месяц:** проверьте, какая модель лучшая и не изменилась ли она; подберите `TREND_WINDOW` (30 / 90 / 180) по бэктесту; зафиксируйте прогноз глубины хранения для планирования закупки дисков.

## 8. Ограничения

- Ни один прогноз не предскажет подключение новых источников или их отключение. После таких событий модели нужно 2–3 недели, чтобы адаптироваться.
- Часовой пояс `_eventDate` и разделов `listpart` не проверен (раздел 2, п. 4).
- Лимит в ноутбуке считается как `DBSPACE × df total`, по описанию tailcutter в документации («92% от общего объёма дискового пространства»). Если в вашей версии tailcutter считает иначе, даты начала ротации будут смещены. Проверить можно по журналу tailcutter в момент первого удаления.
- В режиме гибридного хранилища скрипт собирает `cold_*`, но ноутбук прогнозирует только основной путь. Как tailcutter учитывает холодное хранилище, я не знаю.
